## 0. 设计目标与总原则

operator 会话是 agent 实际动手的那一层：它能调哪些工具、连哪些外部账号、以谁的身份执行，全由会话权限决定。本设计要解决一个具体问题：**让「一个会话能做什么」成为一个显式、可命名、可审计、在创建瞬间冻结的事实**，而不是散落在提示词、环境变量和默认值里的默契。

四条总原则（后文所有条款都是它们的展开）：

1. **默认拒绝（fail-closed）**：任何配置缺失、歧义、损坏、越权，系统的收敛方向永远是「更少权限或不执行」，绝不收敛到「无限制」。
2. **创建时冻结**：会话的权限与连接绑定在创建瞬间由命名策略解析成不可变快照；事后修改策略不溯及既往，会话内改权限只能走显式的版本化更新通道（且受 §3.4 适用范围限定）。
3. **权限面与执行面分离**：决定权限的组件（策略解析器）与使用权限的组件（工具执行器）之间只以快照为契约；执行面无权扩大快照。
4. **拒绝即留痕、拒绝即停止**：每一次拒绝（建会话被拒、更新冲突、执行越界、回调赎回不符）都产生一条只追加的审计事件；执行面收到拒绝后必须停止并上报，不得自行寻找替代路径绕过。

非目标（本设计不做）：多租户计费、跨组织策略继承、工具市场/注册中心本身的设计、OAuth provider 侧的托管实现（那是托管授权层 build-vs-buy 的议题；本文只定义 operator 侧的会话权限与回调校验契约）。注：§2.5 对注册表内容作了信任边界声明——注册表本身的设计不在本文，但三段纪律消费注册表内容，其信任假设必须在本文成文。

术语：

- **工具包（toolkit）**：同一外部服务的一组工具（如某邮箱服务的读/写/搜）。
- **工具（tool）**：可被 agent 调用的单个动作，有唯一名与 JSON Schema 入参定义。
- **命名访问策略（policy）**：见 §1。
- **会话（session）**：一次带身份与权限快照的执行上下文，有唯一 id 与生命周期状态。
- **连接（connection）**：某个内部用户对某个外部服务完成授权后的凭据绑定（蓝图与实例分离：授权配置定义「怎么连」，连接是「谁连了」的实例，token 刷新/吊销是连接的生命周期事件）。

## 1. 命名访问策略（Named Access Policy）

### 1.1 策略对象

策略是一等公民对象，在管理面（Dashboard/API）创建与维护，字段如下：

| 字段 | 说明 |
|---|---|
| `policy_id` | 全局唯一，格式 `sc_` 前缀＋短随机串（如 `sc_9f3ka71d`）。前缀是类型标记：凡在日志、审计、API 载荷里出现 `sc_…`，即知这是一个权限策略引用 |
| `name` | 人类可读名（如「值守-邮箱只读」「cron-舰队-全量」），仅展示，不作寻址 |
| `version` | 单调递增整数，从 1 起；每次策略内容变更 +1，旧版本内容永久可查。各版本可带**版本标记**（见 §1.3：如 `security_contracted` 安全收缩标记） |
| `rules` | 规则集，见 §1.2 |
| `owner` | 负责组别（问责归属，必填） |
| `state` | `draft` / `pending_review` / `active` / `archived`。只有 `active` 可被新会话引用；`pending_review` 为 §1.4 分级复核的中间态（已提交激活、复核未完成），不可被新会话引用 |

### 1.2 规则语义

规则以三个维度声明授予与禁止：`toolkits`（工具包）、`tools`（单个工具）、`tags`（工具标签，如 `read-only`、`destructive`）。每个维度各有一份 `enable` 清单与一份 `disable` 清单。

工具 T 对某策略的**有效判定**按以下确定性顺序求值（任何实现不得偏离此顺序）：

1. 若 T 命中任一 `disable` 规则（工具级、标签级、工具包级任一）→ **禁止**。禁止优先于授予，不设例外通道。
2. 否则，若 T 命中任一 `enable` 规则 → **允许**。
3. 否则 → **禁止**（无正向授予即无权，这是 fail-closed 在策略层的落点）。

推论（有意为之，实现与评审须知）：

- 策略**必须**有正向范围才能被激活：`rules` 三个维度的 `enable` 全空时，策略保存为 `draft` 可以，但置 `active` 时服务端拒绝（错误码见 §6.3），理由是「零授予策略」只能是笔误或误解，不应成为可引用对象。注意这与会话层的「显式空 allowlist」不同（§3.2）：策略层是「不许激活空策略」，会话层是「空 allowlist 是一个合法且严格的运行时语义：零工具」。
- `disable` 用于在宽授予上切口子（如 enable 整个工具包、disable 其中写操作工具），求值顺序保证切口永远生效。
- **引用完整性前提**：上述求值以 rules 引用的工具/工具包/标签真实存在且可解析为前提。该前提不是求值期假设，而是激活期的强制校验——引用不可解析的策略不得进入 `active`，校验规则与处置见 §1.4。尤其是 `disable` 侧引用：拼错一位或目标被改名都会使切口静默落空、作用域静默扩张，因此 disable 侧悬空按危险方向处理（拒绝激活），enable 侧悬空按安全方向处理（告警留痕），两者不得同等对待。

### 1.3 创建时解析、事后不溯及

会话创建请求引用 `policy_id`。服务端在创建瞬间把策略求值成**解析快照（resolved snapshot）**：该会话最终允许的工具集合、判定所需的规则摘要、以及**连接绑定**（见下），快照连同 `policy_id`、`policy_version`、快照哈希一并写入会话记录，此后不可变。快照哈希的计算范围覆盖工具集与连接绑定，任一变化必致哈希变化。

**钉版约束**：创建请求**可以**携带 `policy_version`，但钉版不是任意复活旧作用域的通道：

- 普通调用方：所钉版本必须等于该策略的**当前 active 版本**；钉任何其他版本（含曾经 active 过的历史版本）→ **400 `policy_version_not_pinnable`**，零写入。缺省不带版本时恒取当前 active 版本（语义与钉当前版等同）。
- 合法钉版场景（唯一）：**审计复现**。调用方须持审计角色（§6.2），所钉版本必须曾处于 `active` 且**未带 `security_contracted` 标记**；创建全程留痕（审计事件含调用方、所钉版本、复现事由引用），所建会话在记录上标记 `audit_repro` 以便事后枚举。带 `security_contracted` 标记的版本对任何人（含审计角色）不可钉——审计需要看其内容时走策略历史版本的只读查阅，不建会话。
- **安全收缩标记**：因安全原因收缩策略（删除 enable、新增 disable、收紧至归档）时，执行收缩的管理员**必须**同时把被收缩取代的旧版本标记为 `security_contracted`；标记动作本身写审计事件。未标记的普通内容变更所取代的版本只是普通历史版本（仍不可被普通调用方钉，见上）。
- 本约束与 §3.6 舰队级紧急 blocked 配套，构成「收缩能落地」闭环：收缩管新会话（本条）＋紧急冻结管存量会话（§3.6）＋快照最长寿命管长尾（§3.5）。

**连接绑定冻结**：快照除工具集外还冻结**连接绑定**：

- `connection_bindings`：本会话可使用的连接 `connection_id` 清单。创建时由调用方显式给出（须逐个校验：连接存在、状态 `active`、且 `connection.owner == session.owner`，任一不符整请求拒绝，错误语义同 §3.3）；或显式声明 `connection_mode: none`（不绑连接的会话类型，如纯本地计算会话）——`none` 模式下任何需要连接的工具在执行期一律按无连接拒绝（§2.2）。
- 连接绑定与工具集同等冻结：会话存续期内连接的新增、吊销、替换**不自动改变**已建会话的绑定清单；绑定变更只能走 §3.4 版本化更新（交互式长命会话）或到期重建（舰队会话，§3.5）。执行期如何使用绑定见 §2.2 第三段校验 (c)。

**创建事务性（安全评审（并发专项核查））**：「求值解析＋写会话行＋写快照」必须在**单个事务**内完成：任一步失败整事务回滚，不留无快照的会话行、不留无会话行的孤儿快照。§3.1/§3.3 的零写入保证以此为准。

- 策略之后被修改（version 递增）或归档，**对已建会话零影响**：会话终身按自己的快照执行。这是刻意的：权限变更的影响面必须在变更发生前可枚举（受影响的只有「之后新建的会话」），杜绝「改了一条策略、半夜某个在跑的 cron 突然多出或丢了权限」。唯一的例外是 §3.6 的紧急 blocked——它改的是会话**状态**（置 blocked），不改快照内容，快照不可变原则不破。
- 想让一个存量会话换权限，只有两条路：**新建会话**（推荐，尤其短命任务），或走 §3.4 的**会话配置版本化更新**（显式重解析＋留痕，仅限交互式长命会话，见 §3.4 适用范围）；舰队会话走 §3.5 到期重建。不存在第四条「静默跟随策略最新版」的路。

### 1.4 策略生命周期与治理约束

- `archived` 策略不得被新会话引用（引用即 400，见 §6.3）。
- 被任一未终结会话引用的策略不得物理删除；删除只能走归档（软删除），历史版本内容保留供审计回放。
- 策略的每一次变更（内容、状态、owner）写审计事件，含变更前后 `version`。

**激活分级复核（§9-Q3 定版）**：策略即权限，激活按策略内容分级：

- **宽授予策略**（`enable` 含写操作工具，或命中 `destructive` 标签的工具/工具包）→ 激活须**双人复核**：owner 组负责人提交激活＋**另一组别**复核人批准，两步齐全才转 `active`；中间态为 `pending_review`（§1.1）。复核人不得与提交人同组，更不得为同一人。
- **纯只读策略**（`enable` 全部为只读工具且无 `destructive` 命中）→ 单人激活＋审计留痕即可。
- 激活审计事件必须含**复核人标识**（单人激活含激活人；双人含提交人与复核人双方），无复核人标识的激活事件视为不完整，实现评审按缺项处理。本条的关闭标准在实现评审：管理面须按分级实现两路流程。

**变更方向分级（安全评审，与内容分级合成，冲突标注 C-3 已关闭、定版见 §9-Q3）**：对已 `active` 策略的内容变更按**方向**分级：

- **扩张方向**（新增 enable、删除 disable、纳入写类/`destructive` 工具）→ 变更生成的新版本在生效（被新会话引用）前须第二人复核，复核口径同上（跨组、留痕）；复核未过，新版本停在 `draft` 语义（版本号已占、不可引用）。
- **收缩方向**（新增 disable、删除 enable、归档、§3.6 紧急 blocked）→ 单人即可，且走**快速通道**：不得被复核流程拖慢——fail-closed 方向的动作延迟本身就是风险敞口。
- 两套分级的关系与取舍见 §9-Q3 的 C-3 关闭注（2026-10-16 双门禁确认关闭）：内容分级管「激活」，方向分级管「变更」，重叠时取更严者；只读类扩张变更按更严者＝双人复核。

**审计事件的复核等级决定轴（GC 非约束性注记并入，2026-10-16）**：激活与变更的复核审计事件除复核人标识外（见上「激活分级复核」），还须可辨识本次复核等级由哪一轴决定——内容轴（激活分级）、方向轴（变更分级）、或双轴重叠取更严者（注明以哪一轴为准定级）——使事后审计可追溯某次单人/双人复核的定级来源。此系 GC 确认件的非约束性建议（不构成 C-3 关闭条件），本版采纳为审计事件规格的一部分，实现评审按此验收。

**引用完整性校验**：策略置 `active`（含激活与扩张变更生效）时，服务端必须**全量校验** rules 引用的可解析性（工具名、工具包名、标签名逐项对注册表核对）：

- `disable` 引用不可解析 → **拒绝激活**，**400 `policy_rule_unresolved`**，错误体列出全部不可解析的 disable 引用；策略状态不变（停留在 `draft`/`pending_review`）。
- `enable` 引用不可解析 → 允许激活，但必须产生**告警审计事件**并在激活回执中明示不可解析的 enable 引用（静默变窄可容忍，静默本身不可容忍）。
- 工具改名/下线时，注册表侧必须对**引用该工具的全部 active 策略**做影响面提示（通知各策略 owner 并写审计事件）；若改名/下线会使某 active 策略的 disable 引用变为不可解析，下线动作须先提示该后果，不得让切口在无人知晓时落空。

**有效工具集 diff 展示（安全评审 低建议）**：激活与更新的回执除回显有效工具集与快照哈希（§6.1）外，应展示**相对上一版本的有效工具集 diff**（新增/移除的工具逐项列明）——让复核者审的是生效结果，而不是规则文本。diff 计算以服务端求值为准，不接受调用方自报。

## 2. 元工具三段纪律（Meta-tool Discipline）

### 2.1 默认形态：不预载

广域会话（工具池大、任务开放）默认**不把任何业务工具的定义预载进模型上下文**。会话开局只暴露一组固定的**元工具**（定为六个，按职责而非品牌命名）：

1. `search_tools`：按意图检索候选工具；
2. `fetch_tool_schema`：取某个工具的完整入参 schema；
3. `execute_tool`：执行一个已取过 schema 的工具；
4. `list_connections`：列当前会话快照绑定内的连接（只给标识与状态，不给凭据）；
5. `request_connection`：发起一次连接授权流程（走 §4）；
6. `report_blocked`：执行面主动上报「被权限/连接挡住」并终止本轮动作的结构化出口。

设计动机是上下文预算：工具池规模（数百至上千）与模型上下文之间存在数量级矛盾，把全部定义常驻上下文既不可行也浪费；更重要的是权限面——**没被搜到的工具，对模型不存在**，这让 §1 的允许集合同时成为模型的认知边界。

### 2.2 三段流程

**第一段·搜（search）**：agent 用自然语言意图或关键词查询。服务端只在**本会话快照的允许集合内**检索，返回候选工具的简要描述（名称、用途一句话、关键注意事项：必填字段、分页方式、幂等性）。不允许的工具在结果中**完全不出现**——不给名字、不给「存在但无权」的提示，防止模型把注意力浪费在够不到的工具上，也避免权限面信息泄露。零结果即零结果，agent 应走 `report_blocked` 或换意图，不得反复变词穷举试探。

**第二段·取 schema（fetch）**：agent 对选定工具取完整 JSON Schema。服务端校验该工具在快照内（不在则 403，见 §6.3），返回 schema 并在本会话内缓存（同一会话重复取同一工具可命中缓存，但缓存不跨会话）。**未取过 schema 的工具不得执行**——执行面在收到执行请求时先查本会话的 schema 获取记录，无记录直接拒绝。这保证每一次执行的入参都是照着契约填的。

**第三段·执行（execute）**：`execute_tool` 接收工具名＋入参。执行前执行面做三道校验：(a) 工具在快照允许集合内；(b) 入参通过该工具 schema 的完整校验（类型、必填、枚举、长度）；(c) **连接校验**：该工具若需要连接，实际使用的连接必须出自快照的 `connection_bindings`——调用须显式指明 `connection_id`（可经 `list_connections` 在绑定内挑选），执行面校验该连接在绑定内、`connection.owner == session.owner`、状态为 `active`；任一不符 → **403 `connection_not_in_snapshot`**（与 `tool_not_in_snapshot` 同级），零副作用、写审计。校验全过才把调用发往该连接对应的外部服务，凭据由连接层注入，**凭据永不进入模型上下文与会话记录**。

连接选择的契约（配套）：**不存在服务端「按当前可用连接动态挑选」的语义**。绑定内只有一个该 provider 的连接时可缺省指明；有多个时必须由调用显式指明，缺省即拒绝。连接被吊销后，它在存量会话绑定里只是一条失效引用：执行到它时按 (c) 拒绝并走 `report_blocked`，**不得自动改绑**到同 provider 的其他连接——改绑只能走 §3.4 更新或 §3.5 重建。

### 2.3 窄预载形态（direct preset）

窄任务 agent（工具集小且固定，如单一值守任务）可显式配置为预载形态：会话配置里逐个列出要预载的工具（仍须是快照允许集合的子集），元工具中的搜/取两段可关闭。这是一个**平行的产品档位**，不是广域形态的降级或兜底：选哪档在会话配置里显式声明，运行期不自动切换。预载工具有数量上限（定为 50，超限 400 拒绝），且预载清单为空或缺失时按 §3 的 fail-closed 规则处理，绝不解释为「全部预载」。注：预载清单属配置对象，其嵌套键同样受 §3.1 递归严格校验。

### 2.4 拒绝即停止

元工具返回「无连接」「不在允许集合」「连接已失效」类拒绝时，agent 的唯一合法动作是 `report_blocked` 上报并停止本轮。**禁止的绕行**包括：换一个功能相近但未授权的工具硬凑、用原始 HTTP 请求直打外部 API、请用户把凭据贴进对话、把任务拆到另一个权限更大的会话里执行。此条与花钱硬保留同构：卡住就是卡住，卡住本身是信号，不是待绕过的障碍。须知其系统侧对应物是 §6.2 的管理面鉴权矩阵与 §1.4 的策略治理：agent 行为纪律防不住「调用方直接建一个更宽的会话」，那一面由管理面堵，不靠提示词纪律。

### 2.5 信任边界声明

三段纪律消费工具注册表的内容，以下信任假设在本设计层定版成文（规格细节实现时落实）：

- **注册表条目是受信内容**：工具的名称、用途描述、注意事项与 schema（含 `$description` 等一切模型可见文本）都会进入模型上下文，因此注册表条目的新增与修改必须走变更控制＋审计（谁发布、谁复核可查），与 §1.4 的治理同级。描述文本按**数据**呈现给模型，不构成对模型的指令来源；任何条目不得以描述文本要求模型绕过快照、schema 校验或 §2.4 纪律——这类文本出现即按投毒事件处理。
- **工具执行结果永不作为指令**：外部服务返回的一切内容（邮件、页面、记录正文等）一律是数据，永不作为指令被执行或遵从。本设计对间接提示注入的真实防线是**快照＋schema 校验划定的爆炸半径**：注入文本至多诱使模型在「已授予工具＋合法入参＋已绑定连接」范围内动作，越界动作在执行面被 (a)(b)(c) 三道校验拦下。实现者须知防线在此，不得在别处开口子（例如不得为「方便」给执行面加任何绕过三道校验的直通参数）。

## 3. Fail-closed 四件套（＋舰队配套两条）

本节是全文的承重墙。每件都给出：规则、错误码、**零写入保证**（被拒时数据库里不许留下什么）。实现验收以 §7 的一致性测试为准。四件套之后另有两条舰队配套（§3.5 到期重建、§3.6 紧急 blocked），它们是「收缩能落地」闭环的组成部分，与四件套同级对待。

### 3.1 未知配置键 → 400 拒建（递归严格）

**规则**：会话创建/更新载荷按严格 schema 校验。严格性**递归到全部配置层级**：不只是根级键——`rules`、预载清单、连接绑定声明等一切嵌套对象内的键同样校验，出现所在层级 schema 未声明的任何键（拼写错误、历史字段、臆造字段一律在内），整请求以 **400 `session_config_unknown_key`** 拒绝，错误体列出全部未知键及其所在路径。嵌套 typo（如 disable 条目内字段名拼错）若被静默忽略，语义漂移方向不可控且与悬空引用叠加更危险，故嵌套层级不设「宽容区」。

**零写入保证**：拒绝发生在任何持久化之前——不建会话行、不写快照、不生成会话 id、不触发任何外部调用。唯一允许的落盘是一条只追加的**安全拒绝日志**（记录时间、调用方、未知键名与路径；不记录载荷全文），它属于审计面而非配置面，不构成「部分创建」。拒绝日志的防洪泛与键名落盘卫生见 §10 登记项。

### 3.2 显式空 allowlist = 零工具（归一化已定版）

**规则**：会话/策略载荷里 `enable` 清单有三态，语义互不相同，实现不得混淆：

| 载荷形态 | 语义 |
|---|---|
| 字段缺失（absent） | 解析时按**空清单**处理（fail-closed 归一化，见下） |
| 显式空数组 `[]` | **零工具**：该会话没有任何业务工具可执行（元工具按 §2 形态保留或关闭） |
| 非空数组 | 恰好清单内工具（再与 §1.2 的 disable 求值合并） |

把「显式空」读成「不限制」是权限系统最危险的一类 bug（空集与全集只差一行代码）。本文的归一化方向只有一个：**absent 与 empty 都收敛到零授予**，全集只能由显式非空清单逐项构造，任何默认值都不产生授予。

**定版标注（§9-Q1，2026-10-16）**：absent→empty 归一化已经 GC 门禁与安全评审双轨定版为**全局默认**（GC 留痕件定版、安全评审附条件同意），不再是待裁定问题。两项配套定死：(a) API 文档与管理面文档必须明示该归一化语义（落点 §6.1）；(b) §7 测试 2（absent=empty 归一化回归）为**放行前置**（落点 §7）；(c) 建会话/更新回执必须回显解析后的有效工具集与快照哈希，使「零工具」在回执上可见、可核对（安全评审附条件，落点 §6.1）。实现不得再以「要求显式 `enable`、缺失 400」为由偏离本定版。

**零写入保证**：本条是语义规则而非拒绝规则；但若空 allowlist 与其他非法项同现（如同时引用 archived 策略），整请求仍按对应错误码全拒、零写入。

### 3.3 配置缺失绝不回退无限制会话

**规则**：以下任一情形，系统**失败**而不是降级：

- 创建时引用的 `policy_id` 不存在 → **404 `policy_not_found`**；
- 策略存在但不属于调用方作用域（跨项目/跨组引用）→ **403 `policy_forbidden`**（不泄露策略内容）；
- 策略为 `archived` 或尚在 `pending_review` → **400 `policy_archived`**（未生效同归此类，错误体 reason 区分）；
- 创建时声明的连接绑定校验失败（连接不存在、非 `active`、owner 与会话 owner 不符）→ 整请求拒绝（连接不存在 **404 `connection_not_found`**，其余 **403 `connection_forbidden`**），零写入；
- 运行期加载已存会话的配置/快照失败（记录丢失、校验和不符、存储不可用）→ 会话置 `blocked` 态，执行面拒绝一切工具调用，返回 **503 `session_config_unavailable`**，并触发运维告警。

**铁律**：任何错误路径、重试逻辑、缓存未命中、降级开关，都**不得**把上述情形重试或回退为「无限制会话」。宁可整舰队停摆，不可一艘船无证航行。实现评审时，凡代码里出现「catch 后以默认全量权限继续」的形态，一律按 P0 缺陷处理；实现评审的静态检查清单保留本句原文（安全评审 建议）。

**零写入保证**：创建失败不留会话行与快照；运行期失败不改写会话既有配置，只追加状态事件（`blocked` 及原因）。

### 3.4 更新走乐观并发版本 → 409 零写入（适用范围已定版）

**适用范围（§9-Q4 定版，2026-10-16）**：本条版本化更新**仅适用于交互式长命会话**。会话配置必须显式声明生命周期模式 `lifecycle_mode`，二选一、禁止混用：`versioned_update`（交互式长命会话，走本条）或 `rebuild_on_expiry`（舰队/cron 会话，走 §3.5）。对 `rebuild_on_expiry` 模式的会话发起本条更新 → **400 `session_update_mode_forbidden`**，零写入——舰队的权限变更只经重建生效，不存在「顺手 PATCH 一下舰队会话」的路径。

**规则**：每份会话配置带单调递增的 `config_version`。更新请求必须携带 `expected_config_version`：

- 与当前版本相等 → 在**单个事务**内完成：全量校验（§3.1 递归严格 schema＋§1 语义，含连接绑定的 owner/状态复核）→ 写入新配置（含重解析快照与连接绑定）→ 版本 +1 → 追加一条配置历史记录 → 回执回显新有效工具集、连接绑定与快照哈希（§6.1）。
- 不相等 → **409 `session_config_version_conflict`**，错误体给出当前版本号，提示调用方重读后再决定是否重试。

**零写入保证**：409 时**一个字段都不许落盘**——不写新配置、不动版本号、不追加历史。禁止「能改的先改了」的部分更新。服务端与官方 SDK 都**不自动重试**冲突更新（自动重试会把「我看过旧版、我确认要改」的人类判断稀释成竞态）；重试必须由调用方重读后显式发起。管理面鉴权（谁可 PATCH）见 §6.2 矩阵——乐观并发只防竞态，不防越权，两者不可互相替代。

**历史与回滚**：每个被接受的版本都进只追加的配置历史（版本、快照、操作者、时间、来源请求 id）。回滚不是改历史，而是「以旧版本内容为蓝本生成一个新版本」，历史链保持单调完整，审计可回放任意时刻该会话的权限全貌。

### 3.5 舰队会话到期重建

舰队（cron 等周期性/长命任务）会话定死一种更新节奏：**到期重建**，禁止与 §3.4 混用（§3.4 已从入口堵死）。

- 舰队会话带到期时间，到期即销毁；后续任务实例按**当时的当前 active 策略**重新解析快照、重建会话。权限变更（扩张或收缩）对舰队只经重建生效，不存在原地更新通道。
- **快照最长寿命 ≤24h（安全评审 定版建议，本版采纳为硬上限）**：任何舰队会话的快照自创建起最长 24 小时必须强制到期重建重解析，使策略收缩对全舰队在有界时间（≤24h）内必然生效——这是「创建时冻结」与「收缩能落地」之间的必要平衡阀。会话 TTL 配置可以短于 24h，不得长于 24h；超过上限的 TTL 配置按 §3.1 同级拒绝（400，错误体明示上限）。
- 会话模式在配置里显式声明（`lifecycle_mode: rebuild_on_expiry`），与 §3.4 的二选一互斥由服务端校验。

> **冲突标注 C-1（TTL 数值）——已关闭（2026-10-16）**：关闭依据＝GC 确认件（同日生效）。GC 定性：留痕件的「10 分钟」系**归属错位**——该数值在留痕件中仅出现一处、本绑定其 `session_uri` 一问的对象（理据「可低成本重新发起」只适用于短时可重发对象），系并入转录时串位，从未是 GC 对 cron 舰队长命会话寿命的要求。**定版结论一句：cron 舰队长命会话 TTL 采本版现行口径为正式定版——硬上限 ≤24h（与安全评审舰队快照最长寿命一致），具体值按任务周期类别化配置，短周期任务可用 10 分钟；到期重建为主路径，§3.4 版本化更新限交互式长命会话**；`session_uri` TTL＝单段 10 分钟（C-2 口径不变）；本条状态自确认件起为「机制已落、数值已按本件更正定版」。标注原文要点留档：原标注记 GC 留痕件将 cron 会话到期重建的 TTL 记为「10 分钟」，与同件 `session_uri` TTL 同值，且与「长命会话」语义、与安全评审「舰队快照最长寿命 ≤24h」均不合，本组判断其「高度疑似留痕件笔误（把 session_uri 一问的 10 分钟串写进 cron 一问）」，取舍为原文保留标注、不擅自更正，过渡口径以 ≤24h 为约束上限、TTL 具体值按任务周期配置，并请 GC 在 v0.2 复核轮次中确认——现 GC 已确认（定性为归属错位而非单纯数值笔误，原判断方向成立、定性以 GC 件为准），标注关闭。

### 3.6 舰队级紧急 blocked

策略收缩对存量会话不溯及是刻意取舍（§1.3），但必须有紧急出口，否则某工具被攻陷或某 provider 出事时只能逐个关会话：

- **动作**：持策略管理员或安全角色（§6.2）可按 **policy_id 维度**或**工具维度**批量将受影响的全部未终结会话置 `blocked` 态。blocked 语义与 §3.3 运行期失败一致：执行面拒绝一切工具调用、返回 503 `session_config_unavailable`、触发运维告警。
- **不破冻结原则**：本动作只改会话**状态**、不改任何快照内容；审计事件记录动作人、维度、受影响会话数与事由，被 blocked 的会话逐个追加状态事件。
- **方向分级**：本动作属收缩方向，按 §1.4 方向分级走单人快速通道，不被复核流程拖慢。
- **解封**：blocked 会话的恢复路径见 §10 登记项：只许在快照哈希重新校验通过后解封，禁止人工直接改状态绕过校验，解封留痕。

## 4. OAuth 回调身份校验（防会话固化 · 赎回式＋同意账号归属校验）

### 4.1 威胁模型

连接授权的经典攻击是**会话固化**：发起人 A 生成授权链接，链接被转发/截屏/误发，由另一个人 B 在自己的外部账号上完成同意。若回调直接按「谁完成同意就绑定谁」，B 的外部账号会被绑进 A 的 operator 体系——轻则数据串号，重则 A 借 B 的身份执行操作。根因是把「谁启动」与「谁回来」当成了同一个人。本文用赎回式校验把两者解耦：**完成同意只产生一次性的待赎回凭证，绑定关系要在赎回时以我方登录身份复核后才成立。**

**威胁模型的补全**：v0.1 的赎回校验只验证了 operator 侧的「赎回人＝发起人」，**没有验证 provider 侧同意账号的归属**——按原流程推演：A 发起 → A 把链接转给 B → B 在自己的外部账号上完成同意 → 换出的 token 属于 B 的账号 → A 以 A 的登录态赎回，U′＝U 相符 → 凭据激活、连接归属 A。**本节标题所要防的攻击在原流程下仍然成功。** 因此本设计要求**双侧校验缺一不可**：operator 侧身份复核（赎回人＝发起人）管「谁把连接拿走」，provider 侧同意账号归属校验（§4.2 步骤 4–6）管「拿走的是谁的账号」。同意账号的归属从「从未被检查」改为「记录、明示、确认、留痕」四步齐全（处置规则见 §4.4）。

### 4.2 流程

```
发起方（已登录用户 U）
│ 1. request_connection（可带 declared_account_id：发起人预声明打算绑定的
│ provider 账号标识，如邮箱/sub；声明与否影响步骤 5 的校验强度）
▼
operator 后端 ── 生成 connect_session：
│ · 绑定发起人 user_id = U，并记录 declared_account_id（未声明则为空）
│ · 生成高熵一次性 session_uri（不透明令牌）
│ · 状态 INITIATED，TTL 10 分钟（定版，见 §4.3）
│ 2. 返回授权 URL（含 state = session_uri 的哈希校验值；
│ 授权请求按 §4.3 定版带 PKCE S256 challenge）
▼
用户浏览器 → 外部服务同意页 → 完成同意
│ 3. provider 回调我方 callback（code + state）
▼
callback 处理：
│ · 校验 state 对应一条未过期、状态为 INITIATED 的 connect_session
│ （状态非 INITIATED 的后续回调按单次转移规则处置，见 §4.3：
│ 一律忽略、写审计、不动已封存凭据）
│ · 以 code 换取 token（客户端身份与 PKCE verifier 按 §4.3 定版），
│ 同时从 provider 响应/账号端点读取
│ provider_account_id（sub 优先，其次邮箱），写入 connect_session
│ 4. 同意账号归属预检（封存前执行）：
│ ├─ provider_account_id 命中的已知账号标识
│ │ → 直接产生安全事件，流程转 FAILED：不封存可用凭据
│ │ （换得的 token 立即销毁），写安全事件（见 §4.4）
│ └─ 未命中 → token 封存为「待赎回凭据」（封存即不可变），
│ 状态 → PENDING_REDEMPTION
│ · 浏览器 302 到我方 verifier 端点，仅携带 session_uri
▼
verifier 端点（第一方域名）：
│ 5. 要求浏览器出示我方登录态，得到当前用户 U'
│ · 无登录态 → 跳登录页，登录后回到赎回（TTL 内有效）
│ 6. 赎回判定（双侧校验，顺序执行，任一不符即 FAILED）：
│ ├─ (i) operator 侧：U' == U? 不符 → 凭据销毁、FAILED、安全事件
│ ├─ (ii) 预声明匹配：declared_account_id 非空且 provider 支持标识
│ │ 比对时，provider_account_id == declared_account_id?
│ │ 不符 → 按身份不符处置（凭据销毁、FAILED、安全事件、
│ │ 通用失败页，不泄露期望标识）
│ └─ (iii) 明示确认：赎回页向 U' 「你正在绑定账号
│ <provider_account_id>（provider 名）」，U' 须显式点击
│ 确认绑定——不存在静默激活；未确认即离开 = 未赎回，
│ 凭据保持封存至 TTL 到期销毁
│ 三项全过 → 凭据激活，连接归属 U，状态 ACTIVE，
│ 确认动作写审计事件（含 provider_account_id 标识摘要）
│ session_uri 立即作废
▼
终态：ACTIVE / FAILED / EXPIRED（TTL 到期未赎回，凭据自动销毁）
```

### 4.3 细则

- **令牌卫生**：`session_uri` 是高熵随机值，URL 里除它之外不携带任何用户 id、账号 id、邮箱等标识；服务端只存其哈希，明文只在跳转链中短暂出现。服务端与全链路日志对该参数的脱敏要求见 §10 登记项。
- **TTL 定版（§9-Q2 定版，2026-10-16）**：`session_uri` TTL **定版 10 分钟**，覆盖 INITIATED 与 PENDING_REDEMPTION 两态（单段计时，自 connect_session 生成起算），不预设放宽、不在实现中预留可调放宽开关。误伤兜底定为**低成本重新发起**：过期后发起人可一键/一条命令重新发起授权（新 connect_session），不走人工工单。上线后仅在实测误伤数据显著时凭数据复议，复议走门禁留痕。安全评审提出的两段 TTL 方案与本定版的张力及处置见 §9-Q2 冲突标注 C-2（方案留痕为复议优先议题，本版不采纳）。
- **一次有效**：`session_uri` 在第一次赎回尝试（无论成败）后即作废；重放同一令牌 → **410 `redemption_consumed`**，不改变任何状态，只写审计。
- **状态机单次转移**：connect_session 的状态转移是**单次**的：首次成功换取 token 后，封存凭据**不可变**——PENDING_REDEMPTION 态下再收到携带同一 state 的合法回调（哪怕 code 有效、来自另一个同意账号），一律**忽略并写审计**（不换 token、不覆盖封存、不改状态）；对回调方回 410 语义。此条封死的路径是：链接持有者在他人完成同意后，以另一账号的 code＋同一 state 二次回调，替换待赎回凭据使赎回绑错账号——此路径下连发起人本人都会被坑，故不留任何「后到覆盖先到」的实现自由度。
- **PKCE 与客户端类型定版**：授权码流程定版为：我方服务端 **confidential client ＋ PKCE S256 双保险**，不设豁免。client secret 的存放走凭据红线：存 operator 自有凭据存储（§5.1），**不进 Secure Vault 读回路径**（Vault opaque、读不回明文，与 §5.1 边界句同一口径）。
- **错误分层**：provider 侧的暂时性错误（换 token 时网络失败、provider 5xx）不判死刑——状态保持原态（INITIATED 或 PENDING_REDEMPTION），TTL 内可重试；只有**身份不符（含步骤 4/6 的归属不符）**与**令牌过期/重放**是终局失败。把「暂时故障」与「身份可疑」分开，是为了既不误杀正常用户，也不给攻击者用故障话术要求人工放行的口子。身份不符的安全事件须做告警分级（偶发＝用户误操作量级，聚集＝定向攻击量级），分级规则实现时落实（§10 登记）。
- **身份不符的处置**：不向浏览器透露「期望的用户是谁」「期望的账号标识是什么」；只给通用失败页。安全事件记录发起人、赎回人、provider、同意账号标识摘要、时间，供安全组复核是否定向攻击。
- **与 §1 的关系**：连接只是「凭据可用」，能不能在某会话里用仍由会话快照（含连接绑定，§1.3）决定；新连接的建立不自动进入任何已建会话的绑定清单。

### 4.4 同意账号归属校验的处置规则（定版汇总）

| 情形 | 处置 |
|---|---|
| 同意账号命中另一个已知我方用户的账号标识 | 流程 FAILED；token 不封存（已换得则立即销毁）；安全事件（高优先级）；通用失败页 |
| 有预声明且 provider 支持比对、标识不一致 | 按身份不符处置：凭据销毁、FAILED、安全事件、通用失败页 |
| 有预声明但 provider 不支持标识比对 | 降级为「明示确认」单轨：赎回页明示同意账号标识＋发起人显式确认＋审计留痕；不得静默跳过明示 |
| 无预声明 | 明示确认单轨（同上）：赎回页明示＋显式确认是激活的必经步骤，无静默路径 |
| 代他人绑定（被绑账号不属于发起人，且系有意为之） | 不得走本节自绑流程。单列**代绑流程** `delegated_connect`：被绑账号若属另一我方用户，须由该用户在自己的登录态内另行确认后连接才激活；被绑账号属外部人时，须策略管理员批准＋全程留痕。代绑连接在记录上单独标记，与自绑连接在审计与枚举上可区分 |

### 5.1 connection 凭据存储

**边界句（设计层定版）**：connection 凭据（含 OAuth refresh token、provider API key 等一切需要程序化读回/静默刷新的凭据）存于 **operator 自有凭据存储**，**不经 Secure Vault**——Secure Vault 是 opaque 存储，值只能经批准以引用形式交付、**读不回明文**（我方既有铁律，2026-09-29 实证）；connection 必然要静默刷新 token，走 Vault 会做出一个刷不了 token 的系统，或诱使实现方把 Vault 当可读存储误用。两条凭据通道在本设计中**分开命名、不许混称**：

- **OAuth connection 通道**（本节）：授权码流程建立、服务端托管、自有存储封存、自动刷新轮换；
- **一次性 secret 安装通道**：provider API key 类「只显示一次」的凭据，沿用我方既有一次性安装模式（单次有效安装接口＋盲贴落盘）装入同一自有存储，但其建立流程与 OAuth connection 是两回事，文档与代码中不得互相借名。

规格要点（本版定版方向，参数细节实现时落实并过实现评审）：

- **加密与密钥**：凭据静态加密封存；加密密钥来源、轮换周期与解密权限面（哪些服务身份可解密、以何种审计前提解密）在实现评审中定版，未定版不得接真实凭据。
- **刷新轮换与复用检测**：refresh token 每次刷新即轮换；**旧 refresh token 被重放 = 泄露信号** → 立即告警并将连接置 `revoked`/待复核（验收见 §7 测试 21）。
- **revoke 销毁的验证方式**：吊销须销毁封存凭据且销毁可验证（销毁后以连接 id 尝试读取应返回不存在，验证动作本身留痕），不许只改状态标记而留凭据实体。

## 7. 验收测试清单（实现阶段逐条过）

1. 建会话载荷多塞一个未知键 → 400 且数据库无会话行、无快照行（以行数与哈希双验）；未知键塞在 `rules`/预载清单等**嵌套层级** → 同样 400 并列出路径。
2. **[放行前置——本条不过，整个实现不得放行]** `enable: []` 建会话 → 成功但该会话任何业务工具执行均被拒；把同一载荷的 `enable` 删掉重建 → 行为与空数组**完全一致**（absent=empty 归一化回归）；两次回执均回显空有效工具集与快照哈希（§6.1）。
3. 引用不存在/已归档/他人作用域的策略建会话 → 分别 404/400/403 且零会话行。
4. 人为损坏一条已存会话的快照（改一字节）→ 运行期加载校验失败 → 会话 blocked、零工具可执行、告警发出；任何重试都不产生无限制执行。
5. 两并发更新同基线版本 → 恰一成功；失败者 409，且会话配置的字节级内容与胜者写入前相比除胜者变更外零变化，历史无失败者条目。
6. 回滚：以 v3 内容生成 v7 → 历史链 1..7 完整，v7 快照与 v3 一致（哈希同）。
7. OAuth 固化演练（operator 侧）：U 发起、V 登录赎回 → 连接 FAILED、封存凭据销毁、安全事件含双方 id；同一 session_uri 再赎回 → 410。
8. OAuth 正常路：U 发起、U 赎回（含 §4.2 步骤 6 的明示确认）→ ACTIVE；provider 中途 5xx 一次 → 状态不判死、TTL 内可重试并最终成功（分层错误不误杀）。
9. 搜段隔离：在只授予 A 工具包的会话里搜 B 工具包工具名 → 结果不出现 B 的任何条目；直接 fetch B 工具 schema → 403。
10. 拒绝即停止演练：连接被吊销后执行 → 拒绝上报链完整，执行面无任何替代工具调用记录、无自动改绑记录。
11. 策略 `disable` 引用不存在的工具名 → 激活被拒 `policy_rule_unresolved`、状态不变；`enable` 侧悬空 → 激活通过但告警审计事件＋回执明示齐全。
12. 策略收缩出 v4（v3 已标 `security_contracted`）后：普通调用方新建会话显式钉 v3 → 400 `policy_version_not_pinnable`；审计角色钉 v3 → 同样被拒；审计角色钉未标记的普通历史版本 → 成功且会话带 `audit_repro` 标记、审计事件齐全。
13. 非所有者 PATCH 他人会话配置 → 403 `session_not_owner` 且零写入（配置哈希不变、无历史条目）；无 policy_admin 角色调用 activate → 403 `admin_role_required`。
14. 会话执行时指向未绑定连接 → 403 `connection_not_in_snapshot`＋审计；指向他人名下连接 → 同上；绑定内连接被吊销后执行 → 拒绝且不自动改绑，快照绑定清单不变。
15. A 发起、B 完成同意、A 赎回：(a) 无预声明时，赎回页明示 B 的账号标识、A 显式确认后才 ACTIVE，确认留痕；(b) 有预声明且标识不一致 → FAILED＋凭据销毁＋安全事件；(c) B 的账号命中另一已知我方用户 → 步骤 4 即 FAILED、安全事件先行、无可用凭据封存。
16. PENDING_REDEMPTION 态二次回调（不同 code＋同一 state）→ 封存凭据哈希不变、状态不变、审计有二次回调记录、回调方得 410 语义。
17. execute 入参含 schema 未声明字段 → 422 零副作用。
18. 会话中途工具 schema 变更 → execute 要求重取或按钉版执行（按实现定版断言），不静默漂移。
19. 非幂等工具执行「已执行、响应丢失」后以同幂等键重试 → 只执行一次、结果可重查。
20. 按 policy_id 批量 blocked → 该策略全部未终结会话 503、零工具可执行、告警与审计齐全、快照内容逐字节不变。
21. refresh token 复用（旧 token 重放）→ 检测告警＋连接置 revoked/待复核；revoke 后以连接 id 读凭据 → 不存在（销毁可验证）。
22. verifier 页与全链路日志检查：session_uri 明文不出现在访问日志、代理日志与任何第三方请求中；verifier 页无第三方子资源且带 `Referrer-Policy: no-referrer`。

## 8. 审计与日志边界

审计事件覆盖：策略创建/变更（含方向分级与复核人标识，§1.4）/激活（含复核人标识）/归档/引用完整性告警、会话创建（含快照哈希、钉版与审计复现留痕）/更新/冲突被拒/blocked（含 §3.6 紧急 blocked 的动作人、维度与受影响会话数）/关闭、工具执行被拒（含连接校验被拒）、连接发起/同意账号归属预检命中/赎回成功（含明示确认留痕）/赎回不符/代绑确认/吊销、回调单次转移违规（二次回调）。日志只记标识符与结果码，不记工具入参、响应正文、凭据与外部账号明文标识（外部账号以标识摘要入审计）——「记什么」从紧，「不记什么」明示，是本设计对隐私红线文档的接口：operator 侧先把自己的边界划清，上层文档再汇总对外声明。

## 9. 已定版问题（原「待评审问题」，2026-10-16 双门禁定版）

本节四问已由 GC 门禁定版（定版载体：GC 留痕件）并逐问吸收网络安全组安全评审的意见，不再是开放问题；实现不得带本节任何疑问另行解释。逐问格式：定版结论／安全侧意见与吸收／落点。

### Q1 absent→empty 归一化 —— 已定版

- **定版结论**：接受 absent→empty 归一化为全局默认（省略即零授予，不要求显式 `enable`、缺失不 400）。配套定死：API 与管理面文档须明示该语义；§7 测试 2 列为放行前置。
- **安全侧意见与吸收**：安全评审 **同意**同一取向（两取向收敛方向都是零授予，安全性等价；强制显式反而诱发上层模板默认值代填），附一条件：建会话/更新回执必须回显解析后的有效工具集与快照哈希——已吸收为 §6.1 回执回显要求，并在测试 2 中断言。无冲突。

### Q2 session_uri TTL 10 分钟 —— 已定版（含冲突标注 C-2）

- **定版结论**：TTL 定版 10 分钟（单段，自 connect_session 生成起算，覆盖 INITIATED 与 PENDING_REDEMPTION 两态），短 TTL 是安全属性，不预设放宽、不预留可调开关；动线误伤以「低成本重新发起」兜底；上线后实测误伤显著时凭数据复议、走门禁留痕。
- **安全侧意见**：安全评审 建议**拆两段**：发起→回调 10 分钟保持（压链接转发窗口）；回调完成→赎回另给独立 30 分钟窗口——理由是待赎回凭据为惰性、赎回仍需发起人登录态，多给时间不显著增险，却适配「手机上完成同意、再回电脑赎回」的真实动线。
- **冲突标注 C-2（显式标注）**：GC 定版（单段 10 分钟）与安全侧建议（两段 10＋30 分钟）在赎回窗口长度上不一致。**本版取 GC 定版**，理由：(1) GC 留痕件是本问指定的定版载体，本问的定版权在 GC，安全评审对本问的措辞是「建议」而非其实现前强制项；(2) GC 定版自带复议通道（凭实测误伤数据再议），安全侧方案不会被静默丢弃——**本标注即其留痕：上线后若触发误伤复议，复议议程的第一议题即两段拆分方案**，复议结论走门禁留痕后修订本节；(3) 单段短 TTL 在复议前保持更严的收敛方向，与总原则 1 一致。本标注由 GC 与安全组在 v0.2 复核时共同确认后关闭。

### Q3 策略管理权限与双人复核 —— 已定版（冲突标注 C-3 已关闭）

- **定版结论**：策略激活分级复核——enable 含写操作或 `destructive` 标签的宽授予策略激活须双人复核（owner 组负责人＋另一组别复核人）；纯只读策略单人激活＋审计留痕；激活审计事件含复核人标识。角色面由 §6.2 鉴权矩阵一并定版：建/改/激活/归档限 policy_admin。
- **安全侧意见**：安全评审 要求设角色＋**按变更方向分级**：凡有效集扩张（新增 enable、删 disable、纳入 destructive/写类）的变更与激活须第二人复核后生效；收缩方向（归档、加 disable、紧急 blocked）单人即可且走快速通道——fail-closed 方向不许被流程拖慢。
- **冲突标注 C-3——已关闭（2026-10-16）**：关闭依据＝GC 确认件（确认采纳，关闭）＋网络安全组复核件（附条件确认）。**定版结论一句：双维度合成定版——内容分级管「激活」、方向分级管「变更」，重叠时取更严者；只读类扩张变更＝双人复核**（授予面扩大不因「只读」二字降格）。安全组附带一条实现期条件（属实现评审关闭项，不阻塞本标注关闭）：方向分级的判定基准须在实现评审定版为**服务端求值的有效工具集 diff**（§1.4 已定 diff 以服务端求值为准，本条件要求该口径同时适用于方向判定本身），不许只按规则文本的增删字面判定——防「换名不换量」的文本级伪装骗过方向判定；该条件已转入实现启动简报关闭清单（C-3 实现期条件）。标注原文要点留档：两边分级维度不同——GC 按**策略内容**分级（管「激活」这一刻的策略长什么样），安全侧按**变更方向**分级（管「这一次改动把有效集推向哪边」）；本版判断两者不在同一轴上、不构成非此即彼，双维度同时采纳——激活看内容（§1.4 激活分级复核），变更看方向（§1.4 变更方向分级），同一动作同时触发两套分级时取更严者（双人复核）；唯一真实张力在「只读但属扩张」的变更（如给只读策略新增一个只读工具包）：GC 口径下其激活为单人，安全侧口径下其变更属扩张须双人——原取舍为按「取更严者」以双人复核落地，并请两门禁在 v0.2 复核时确认；现已经两门禁确认，取舍即定版，标注关闭。

### Q4 cron 长命会话的权限更新节奏 —— 已定版（TTL 数值已定版，见 §3.5 C-1 关闭注）

- **定版结论**：定死一种、禁止混用——cron/舰队长命会话走**到期重建**（到期销毁、按当前策略重新解析快照重建，权限变更只经重建生效），禁止走 §3.4 原地更新；§3.4 乐观并发版本化更新仅限交互式长命会话。两种模式在会话配置里以 `lifecycle_mode` 显式声明，服务端校验互斥。
- **安全侧意见与吸收**：安全评审与 GC 同向（舰队一律到期重建、不走原地更新、模式显式声明禁混用），并加一条**舰队快照最长寿命 ≤24h**（到期强制重建重解析，使策略收缩对全舰队有界生效）——已吸收为 §3.5 硬上限，与舰队级紧急 blocked 配套构成收缩闭环。
- **TTL 数值（原冲突标注 C-1，已关闭 2026-10-16）**：GC 确认件定性为归属错位并定版——cron 舰队长命会话 TTL 硬上限 ≤24h、具体值按任务周期类别化配置（短周期任务可用 10 分钟）、到期重建为主路径；关闭注全文见 §3.5。
